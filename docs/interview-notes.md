# 면접 대비 노트

> 설계·구현 과정에서 나온 기술 판단을 면접 질문 형태로 정리한 것.
> **구현하면서 실제 숫자와 겪은 문제를 계속 채워 넣을 것.** 숫자 없는 답변은 절반의 답변이다.

## 0. 프로젝트 한 줄 소개

> "사진을 중심으로 하루를 기록하는 개인 아카이브를 만들었습니다.
> 규모는 개인용이라 작지만, 한 번의 업로드가 수 GB에 영상 트랜스코딩이 섞여 있어서
> **부분 실패와 재개**가 핵심 문제였습니다."

**목표는 상대가 "그거 어떻게 했어요?"라고 되묻게 만드는 것.**
"기록 플랫폼 만들었습니다"로 끝나면 대화가 안 이어진다.

### 왜 만들었나 (동기 질문)

매일 아날로그로 일기를 쓰고 매달 2~3회 블로그에 사진 기록을 남기는데,
사진을 고르고 순서를 정하는 데 시간이 오래 걸렸다.
그런데 그 과정을 좋아하는 이유는 **사진을 보며 기억을 떠올리기 때문**이었다.

그래서 "떠올리는 시간은 남기고 배치하는 노동만 없앤다"를 설계 원칙으로 잡았다.
AI도 같은 이유로 문장을 대신 쓰지 않고 뼈대와 질문만 제시하게 했다.

## 1. 아키텍처 판단

### Q. 왜 Kafka나 RabbitMQ를 안 썼나요?

**작업 큐를 PostgreSQL 테이블 + `FOR UPDATE SKIP LOCKED`로 구현했습니다.**

가장 큰 이유는 **트랜잭션 일관성**입니다. 미디어 자산을 생성하는 것과 처리 작업을 등록하는 것이 같은 트랜잭션에 묶여서, "자산은 생겼는데 작업이 유실됨"이 구조적으로 불가능합니다. 브로커를 쓰면 이걸 보장하려고 아웃박스 패턴을 따로 만들어야 하는데, 그건 결국 DB 큐를 한 겹 더 얹는 셈입니다.

부차적으로는 운영 컴포넌트가 하나 줄어서 로컬 개발과 통합 테스트가 가벼워집니다.

**도입 조건도 정해뒀습니다** — 워커가 여러 대로 늘어 DB 폴링이 부담되거나, 처리량이 초당 수백 건을 넘으면 그때 전환합니다. 지금 규모에서 브로커의 처리량 이점은 의미가 없었습니다.

### Q. Redis는요?

**안 썼습니다.** 쓸 자리를 하나씩 검토했는데 전부 대안이 있었습니다.

| 용도 | 대안 |
|---|---|
| 세션 | 소셜 로그인 + httpOnly 쿠키 |
| 캐시 | 개인 서비스라 캐시 압력 자체가 없음 |
| 작업 큐 | PostgreSQL `SKIP LOCKED` |
| 분산 락 | 워커가 소수라 DB 행 락으로 충분 |
| 실시간 알림 | **PostgreSQL LISTEN/NOTIFY** |

특히 마지막이 재밌었는데, 워커와 API 서버가 다른 프로세스라 알림 채널이 필요했습니다. 보통 Redis pub/sub을 쓰는데, Postgres에 LISTEN/NOTIFY가 내장돼 있어서 그걸로 해결했습니다.

### Q. 왜 MinIO인가요?

S3 호환 오픈소스 스토리지라 **로컬 개발과 운영이 같은 코드**가 됩니다. AWS SDK를 그대로 쓰고 엔드포인트만 바꾸면 실제 S3로 전환됩니다. Testcontainers에 MinIO 이미지가 있어서 통합 테스트에서 진짜 스토리지를 띄울 수 있는 것도 컸습니다.

그래서 **MinIO 자체 SDK(`io.minio`)를 쓰지 않고 AWS SDK v2를 썼습니다.** MinIO 전용 SDK가 API는 더 단순한데, 그걸 쓰면 스토리지를 바꿀 때 클라이언트 코드를 다시 쓰게 됩니다. 이 프로젝트에서 MinIO는 목적이 아니라 로컬에서 S3를 흉내내는 수단이라, 코드가 의존해야 하는 건 S3 API 쪽이었습니다.

덕분에 하나 더 얻었습니다. 스토리지 계층을 세 층으로 나눴는데(해시·키 규칙 / 바이트 입출력 / 중복 판단), **층마다 검증 방법이 달라집니다.** 키 규칙은 순수 함수라 컨테이너 없이 단위 테스트로 끝나고, 컨테이너가 필요한 건 가운데 층뿐입니다. 원격 데몬을 쓰는 환경에서는 이 구분이 그대로 반복 속도가 됩니다.

### Q. JPA를 안 쓰고 Spring Data JDBC를 쓴 이유는?

**이 프로젝트의 핵심이 전부 SQL 쪽에 있었기 때문입니다.**

작업 큐의 `FOR UPDATE SKIP LOCKED`, 블록 순서키의 fractional index, stage 멱등성 — 세 가지 다 JPA로 가면 결국 native query로 빠집니다. 그러면 JPA를 쓰는 의미가 절반은 사라집니다.

결정적이었던 건 **결정론**입니다. 이 프로젝트는 불변식 테스트와 에이전트 자동 수정 루프가 중심인데, 둘 다 "같은 입력이면 같은 결과"를 전제로 합니다. 영속성 컨텍스트가 있으면 flush 시점에 따라 발생 SQL이 달라지고, 특히 **멱등성 테스트가 위험합니다** — 두 번째 실행이 1차 캐시에 막혀 DB까지 가지 않으면 테스트가 통과하지만 실제로는 검증된 게 없습니다.

**버린 쪽도 압니다.** 연관관계 매핑과 더티 체킹을 직접 써야 해서 단순 CRUD 코드는 JPA보다 깁니다. 그 대신 발생하는 쿼리가 코드에 그대로 보입니다.

> 💡 실측 후 채울 것: Data JDBC로 인해 늘어난 보일러플레이트의 실제 분량

### Q. Spring Boot 4를 쓰셨네요? 3이 더 안정적이지 않나요?

**시작 시점에 3.x는 이미 전 브랜치가 OSS 지원 종료 상태였습니다.** 3.5가 2026년 6월 30일에 EOL 됐고, 무료 보안 패치를 받는 건 4.0과 4.1뿐이었습니다.

처음엔 저도 3이 안전하다고 생각했는데, 확인해보니 **"안정적"과 "지원됨"이 다른 이야기**였습니다. 3.5가 안정적인 건 맞지만 새 CVE가 나와도 패치가 안 옵니다. 실제로 제가 매일 쓰는 서비스라 그건 감수하기 어려웠습니다.

3→4가 어렵다는 이야기는 많이 봤습니다. Jackson이 3으로 올라가면서 패키지가 `com.fasterxml.jackson`에서 `tools.jackson`으로 옮겨졌고, 자동설정 JAR이 70여 개로 쪼개졌고, 3.5에서 deprecated였던 API가 전부 삭제됐습니다. **그런데 그건 기존 코드를 옮길 때 드는 비용입니다.** 저는 빈 프로젝트에서 시작했으니 해당이 없었습니다.

**실제로 치른 비용은 다른 쪽이었습니다.** 검색하면 나오는 예제가 대부분 아직 Boot 3 기준이라, 스타터 이름이 바뀐 걸 모르고 `spring-boot-starter-web`을 썼다가 막혔습니다. 4에서는 `spring-boot-starter-webmvc`이고, Flyway도 `spring-boot-starter-flyway`를 따로 넣어야 자동설정이 붙습니다.

### Q. 개발 환경에서 어려웠던 점은?

**로컬에 Docker를 둘 수 없어서 Testcontainers가 원격 데몬을 쓰게 만들었습니다.**

`DOCKER_HOST`로 서버 데몬을 가리키면 컨테이너는 서버에 뜹니다. 그런데 **컨테이너를 만드는 곳과 접속하는 곳이 갈라집니다.** JDBC 연결은 여전히 `localhost`를 두드려서 계속 타임아웃이 났고, `TESTCONTAINERS_HOST_OVERRIDE`로 접속 주소를 따로 알려줘야 한다는 걸 알고 나서야 풀렸습니다.

여기서 배운 게 하나 더 있는데, **바인드 마운트를 못 씁니다.** 경로가 서버 기준으로 해석되니까요. 그래서 골든셋 파일을 컨테이너에 마운트하는 대신 JVM이 직접 읽어 스토리지에 올리도록 짰는데, 결과적으로 실제 업로드 경로와 같은 모양이 돼서 테스트가 더 정직해졌습니다.

**측정치**: 통합 테스트 4건에 Postgres 컨테이너 기동까지 포함해 **23초**입니다.

다만 **"원격이라서 얼마나 느려졌나"는 말할 수 없습니다.** 비교할 로컬 데몬이 애초에 없어서
기준선이 없거든요. 이건 측정의 한계로 그냥 인정하고 있습니다. 대신 컨테이너를 테스트 클래스마다
띄우지 않고 정적 싱글턴으로 한 번만 띄우도록 했는데, 기동 비용이 로컬보다 크다는 전제에서는
이쪽이 확실히 이득입니다.

## 2. 업로드

### Q. 클라이언트가 보낸 해시를 어떻게 신뢰하나요?

**신뢰하지 않습니다. 서버에서 재계산합니다.**

다만 검증하려고 방금 올린 200MB 객체를 다시 다운로드하면 낭비입니다. 그래서 **`PROBE` 단계에 검증을 합쳤습니다.** 어차피 EXIF를 읽으려고 파일을 스트리밍하니, 읽는 김에 SHA-256을 같이 계산합니다. 추가 I/O가 사실상 0입니다.

그래서 상태가 `UPLOADED`(바이트 수신)와 `VERIFIED`(검증 통과)로 나뉩니다.

### Q. 저장하는 도중에 바이트가 깨지면요?

**스토리지가 대신 잡아 줍니다.** 객체를 올릴 때 `x-amz-checksum-sha256` 헤더에 우리가 계산한 해시를 함께 보내면, S3(MinIO)가 수신한 바이트로 SHA-256을 다시 계산해 대조하고 다르면 저장을 거부합니다.

이게 마음에 들었던 이유는 **직접 확인하려면 방금 올린 걸 다시 내려받아야 한다**는 점입니다. 원본이 수백 MB인데 검증하려고 왕복을 두 번 하면 처리 시간이 두 배가 됩니다. 규격에 이미 있는 기능이라 비용 없이 같은 보장을 받았습니다.

**여기서 함정을 하나 밟았습니다.** 반대로 "스토리지가 보관 중인 체크섬"을 읽어오는 건 안 됐습니다. `HeadObject` 응답에 체크섬 필드가 계속 비어 있어서 처음엔 MinIO가 SHA-256을 보관하지 않는다고 결론지었는데, 아니었습니다. **요청에 `checksumMode=ENABLED`를 넣지 않으면 스토리지가 체크섬 헤더를 아예 보내지 않습니다.** 기본값이 꺼짐이라는 걸 몰랐던 것이고, 저장은 처음부터 잘 되고 있었습니다.

이 값이 중요한 건 **무결성 감사** 때문입니다. 원본 수천 개가 멀쩡한지 확인해야 하는데, 값을 읽을 수 있으면 바이트를 한 번도 내려받지 않고 훑을 수 있습니다. 대신 "저장이 정말 온전한가"를 확인할 때는 실제 바이트를 다시 읽습니다 — 검증 대상에 스토리지 자신이 포함되는 상황에서 스토리지의 주장을 근거로 삼으면 아무것도 검증하지 못하니까요.

### Q. 업로드 재개는 어떻게 구현했나요?

**두 층위로 나뉩니다.**

| 상황 | 동작 |
|---|---|
| 네트워크 끊김 (같은 화면) | `chunk_bitmap`으로 미수신 청크만 재전송. **완전 자동** |
| 탭 닫고 재방문 | 파일 재선택 필요. 단 **해시 조회로 완료분은 재전송 0바이트** |
| 탭 닫은 채 백그라운드 업로드 | 불가능 (웹 플랫폼 한계). `beforeunload`로 이탈 경고 |

두 번째가 재밌습니다. 브라우저는 페이지를 벗어나면 `File` 객체를 잃어서 파일을 다시 선택받아야 하는데, **내용 해시 기반 중복 제거 덕분에 이미 올라간 43장은 한 바이트도 다시 안 보냅니다.** 사용자는 다시 고르는 수고만 하고 3GB를 아낍니다.

### Q. 재개할 때 이미 올라간 사진은 화면에 어떻게 나오나요?

**중복 사진이 오히려 가장 빨리 뜹니다.** 해시가 이미 있다는 건 자산도 썸네일도 이미 존재한다는 뜻이라, 해시 조회 응답에 썸네일 키를 같이 실어 보냅니다. 전송도 처리도 없으니 수백 밀리초입니다.

이게 재개 UX의 핵심이었습니다. 파일을 다시 선택했는데 화면이 비어 있으면 사용자는 "처음부터 다시 올라가나?" 하고 불안해합니다. 완료된 43장이 즉시 뜨면 **"이어서 하는구나"가 시각적으로 전달됩니다.**

기존 자산이 아직 처리 중이면 `assetId`만 주고 SSE를 기다리게 하고, 처리가 실패한 상태면 **재업로드가 아니라 처리 작업만 다시 등록합니다** — 원본 바이트는 멀쩡하고 실패한 건 처리 단계니까요.

### Q. 브라우저에서 4GB 파일 해싱을 어떻게 했나요?

**여기서 함정을 하나 밟았습니다.** 브라우저 내장 `crypto.subtle.digest`는 **스트리밍을 지원하지 않습니다.** 전체 `ArrayBuffer`를 한 번에 받아야 해서 큰 파일에서 메모리가 터집니다. 사진 테스트는 전부 통과하는데 영상에서 탭이 죽었습니다.

WASM 기반 스트리밍 해시 구현(`hash-wasm`)으로 바꾸고 Web Worker에서 돌렸습니다. `file.stream()`으로 청크를 읽으며 `update()`를 반복하니 메모리는 청크 하나분만 씁니다.

추가로 **해싱과 업로드를 파이프라인화**했습니다. 전부 해싱한 뒤 올리면 초반 수 초가 죽는데, 계산이 끝난 파일부터 바로 올리게 하니 첫 사진이 훨씬 빨리 화면에 뜹니다. 이걸 위해 API도 바꿨습니다 — 세션 생성 시 해시를 다 받지 않고, 파일별로 계산되는 대로 개별 보고받는 구조로요.

## 3. 처리 파이프라인

### Q. 사진과 영상을 왜 다른 큐로 나눴나요?

**헤드 오브 라인 블로킹 때문입니다.**

워커 4개에 사진 66장 + 영상 4개를 넣으면, 큐 앞쪽 영상 4개를 워커 4개가 전부 물고 2분간 놓지 않습니다. 그동안 사진 66장은 하나도 처리되지 않고 화면이 비어 있습니다.

레인을 나눠 사진 워커 3 + 영상 워커 1로 두니, 사진은 20초 만에 다 뜨고 영상은 뒤에서 천천히 익습니다. 사용자는 사진을 보며 글을 쓰기 시작할 수 있습니다.

### Q. 처리 단계를 왜 여러 개로 나눴나요?

**빠른 정보를 먼저 주기 위해서입니다.**

`PROBE`는 20ms면 끝나고 여기서 촬영시각이 나옵니다. 그 순간 사진을 시간순으로 배열할 수 있어요 — 썸네일이 없어도 자리는 잡힙니다. 이어서 `THUMB`이 끝나는 대로 그림이 채워지고, 무거운 `DERIVE`는 백그라운드에서 돕니다.

한 덩어리로 묶으면 몇 분간 아무것도 안 보이다가 한꺼번에 뜹니다. 그동안 사용자는 고장 난 줄 압니다.

**실패 단위를 좁히는 것**도 이유입니다. 트랜스코딩만 실패했으면 `DERIVE`만 재시도하면 됩니다.

### Q. 워커가 죽으면 어떻게 되나요?

`locked_at`이 2분 이상 지난 `RUNNING` 작업을 회수합니다.

**그런데 여기 함정이 있었습니다.** 영상 트랜스코딩은 정상적으로도 2분이 걸립니다. 회수 기준을 2분으로 잡으면 멀쩡히 일하는 워커의 작업을 빼앗게 되고, 기준을 10분으로 늘리면 진짜 죽었을 때 10분을 방치합니다.

**하트비트로 해결했습니다.** 워커가 30초마다 `locked_at`을 갱신하니, 회수 기준을 2분으로 짧게 유지하면서도 긴 작업이 안전합니다.

거기에 작업 완료 시 소유권을 확인합니다.

```sql
UPDATE processing_jobs SET state='DONE'
 WHERE id = :jobId AND locked_by = :workerId;   -- 0행이면 뺏긴 것
```

0행이면 다른 워커가 이미 가져간 것이므로 결과를 버립니다.

### Q. 같은 작업이 두 번 실행되면요?

**반드시 일어나는 일로 보고 설계했습니다.** lease 만료로 회수된 작업이 사실 완료 직전이었을 수 있으니까요.

- `PROBE` — 순수 함수. 같은 메타를 덮어씀
- `THUMB`/`DERIVE` — **`storage_key`를 내용 해시 기반으로 결정론적으로** 만들어 같은 자리에 덮어씀
- derivatives 행 — `ON CONFLICT DO UPDATE`로 UPSERT

`storage_key`에 랜덤 UUID를 쓰면 재실행마다 새 객체가 생기고 이전 것이 고아가 됩니다. 해시 기반이라 쓰레기가 안 남습니다.

### Q. 모든 실패를 재시도하나요?

**아니요, 분류합니다.**

| 분류 | 예시 | 처리 |
|---|---|---|
| 일시적 | 스토리지 타임아웃, 연결 끊김 | 지수 백오프 재시도 |
| 영구적 | 손상 파일, 미지원 코덱, 해시 불일치 | 즉시 `DEAD` |

영구 실패를 재시도하면 5번 헛돌며 5분을 낭비하고 그동안 큐가 막힙니다.

백오프는 1s → 4s → 16s → 64s → 256s인데, **full jitter를 넣었습니다.** 작업 50개가 동시에 실패하면 백오프가 같아서 재시도도 동시에 몰립니다 — 죽어가는 스토리지에 확인사살이죠. `random(0, base)`로 흩뿌리니 몰림이 사라졌습니다.

## 4. 실시간 알림

### Q. Redis 없이 실시간 알림을 어떻게 했나요?

**PostgreSQL LISTEN/NOTIFY**입니다. 워커가 `NOTIFY media_events, '{...}'`를 보내면 API 서버가 `LISTEN`으로 받아 SSE로 브라우저에 전달합니다.

주의할 점이 셋 있었습니다.
- **전용 커넥션이 필요합니다.** 풀에서 빌려 쓰면 반납 시 LISTEN이 사라집니다
- 페이로드 8000바이트 제한 — ID만 보내고 상세는 수신 측이 조회
- **내구성이 없습니다.** 구독자가 없는 동안의 알림은 사라집니다

### Q. 알림이 유실되면 화면이 틀리지 않나요?

**SSE를 최적화로만 취급하고 정확성의 근거로 삼지 않았습니다.**

클라이언트는 SSE와 별개로 5초마다 세션 상태를 전체 조회합니다. 알림을 놓쳐도 5초 안에 수렴합니다.

이 원칙을 세우니 SSE가 끊기든, 서버가 재시작하든, NOTIFY가 유실되든 화면이 결국 맞아집니다. **실시간 채널을 신뢰의 근거로 삼는 순간 온갖 엣지 케이스가 버그가 됩니다.**

### Q. 연결이 계속 열려 있으면 관리가 필요하지 않나요?

**keepalive를 넣어야 했습니다.** 프록시나 로드밸런서는 데이터가 안 흐르는 연결을 30~60초 유휴로 보고 끊는데, 영상 트랜스코딩 2분 동안은 보낼 이벤트가 없습니다. 그래서 15초마다 SSE 코멘트(`: ping`)를 보냅니다. 규격상 무시되지만 바이트는 흐르니 유휴 판정을 피합니다.

닫는 시점은 세션의 모든 자산이 `READY`가 되거나 편집 화면을 벗어날 때입니다. 서버 타임아웃이나 네트워크 끊김으로 닫히는 경우는 **브라우저가 알아서 재연결합니다** — WebSocket이었으면 직접 짜야 했을 부분입니다.

### Q. WebSocket이 아니라 SSE를 쓴 이유는?

필요한 방향이 서버 → 클라이언트 단방향뿐이었습니다. 업로드는 일반 HTTP로 하니까요.

SSE는 그냥 HTTP라 프록시를 잘 통과하고 **브라우저가 재연결을 알아서 해줍니다.** WebSocket이면 연결 관리·하트비트·재연결을 직접 짜야 하는데, 얻는 게 없는 양방향이었습니다.

## 5. 데이터 모델

### Q. 블록 순서를 왜 정수로 안 했나요?

**fractional index(문자열 순서키)를 썼습니다.** `"a0" < "a0V" < "a1"` 처럼 사전순으로 정렬됩니다.

정수 인덱스면 블록 사이에 하나 끼울 때마다 **뒤쪽 전체를 UPDATE**해야 합니다. 이 서비스는 이미 쓴 글 중간에 사진을 추가하는 게 핵심 동작이라 삽입이 잦고, 자동저장과 겹치면 충돌이 폭증합니다.

문자열 순서키는 두 키의 중간값을 만들어 **INSERT 한 번**으로 끝납니다. 다른 블록은 손도 안 댑니다.

검증도 됩니다 — 임의의 삽입·이동·삭제 시퀀스에 대해 "순서키가 유일하고 정렬이 보존된다"를 속성 기반 테스트로 돌렸습니다.

### Q. 사진 ID를 왜 JSONB payload에 안 넣었나요?

별도 조인 테이블(`record_block_media`)로 뺐습니다. 이유가 셋입니다.

- **역추적** — "이 사진이 어떤 기록에 쓰였나"가 인덱스 한 방에 나옵니다. JSONB 안에 있으면 모든 블록을 뒤져야 합니다
- **참조 무결성** — 자산을 지워도 JSON 속 UUID는 남아 깨진 참조가 됩니다
- **삭제 판정** — 고아 자산 스윕이 이 테이블을 기준으로 동작합니다

### Q. 파생물에 왜 버전을 붙였나요?

**무중단 백필과 롤백을 위해서입니다.**

썸네일 알고리즘을 바꾸면 이미 만든 수천 장을 재처리해야 하는데, 버전이 없으면 전부 지우고 다시 만들어야 합니다. 재생성 중엔 화면이 깨지고, 결과가 나빠도 되돌릴 수 없습니다.

버전이 있으면 v1을 그대로 둔 채 v2를 천천히 만들고, 조회는 "v2 있으면 v2, 없으면 v1"로 폴백합니다. 재처리 중에도 화면이 멀쩡하고 롤백은 v2를 버리면 끝입니다.

그리고 **같은 원본 + 같은 레시피 버전이면 항상 같은 바이트**가 나오게 만들었습니다. 이게 성립하면 파생물은 데이터가 아니라 캐시라서 백업 대상에서 빠집니다.

### Q. 왜 미디어와 기록을 분리했나요?

분리라기보다 **참조로 연결**한 것입니다. 오히려 관계가 더 명확해집니다.

실무적으로는 업로드 시점과 기록 배치 시점이 다르기 때문입니다. 파일이 올라와 처리되는 동안은 아직 어떤 블록에도 속하지 않은 중간 상태가 존재하는데, 종속 모델로는 이걸 표현할 수 없습니다.

## 6. 삭제와 정합성

### Q. 사진을 지우면 원본은 어떻게 되나요?

**30일 유예 후 물리 삭제**입니다. 그 전엔 "최근 삭제된 항목"에서 복구할 수 있고, 즉시 완전 삭제도 가능합니다.

영구 보관하지 않는 이유는 단순합니다 — 사용자가 지웠는데 서버에 남아 있으면 "지웠다"는 말이 거짓이 됩니다.

### Q. 여기서 어려웠던 점은?

**내용 해시로 저장하니 물리 파일은 하나인데 참조가 여럿일 수 있다는 점**입니다. 기록 A에서 지웠다고 파일을 삭제하면 기록 B의 사진이 깨집니다.

그래서 삭제 판정을 "사용자가 지웠나"가 아니라 **"참조가 0인가"**로 바꿨습니다.

참조 카운트 컬럼은 쓰지 않았습니다. 동시에 여러 곳에서 증감하면 어긋나고, 한번 어긋나면 복구 방법이 없습니다. **주기적으로 실제 참조를 세는 스윕**은 느리지만 자가 치유됩니다.

### Q. 삭제 순서도 고민했나요?

**DB 먼저, 스토리지는 나중에.** 원칙은 "덜 위험한 실패 쪽으로 순서를 정한다"입니다.

| 순서 | 중간 실패 시 | 심각도 |
|---|---|---|
| 스토리지 → DB | DB엔 있는데 파일 없음 = **깨진 참조** | 치명적 |
| DB → 스토리지 | 아무도 안 가리키는 **고아 파일** | 경미, 스윕이 회수 |

### Q. 가장 잡기 어려웠던 버그는?

**삭제 유예 중인 자산을 다시 업로드하는 경우**입니다.

30일 유예 중인 자산의 해시가 중복 조회에 걸립니다. 그대로 재사용하면 **곧 삭제될 파일을 새 기록이 참조하게 되고, 30일 뒤에 사진이 조용히 사라집니다.**

재현에 30일이 걸리는 종류라 실전에서는 잡기 최악입니다. 중복 판정 시 `orphaned_at`을 되살리는 처리를 넣고 테스트로 못 박았습니다.

## 7. 동시성

### Q. 여러 기기에서 동시에 편집하면?

`records.version`으로 낙관적 락을 걸었습니다. 저장 시 클라이언트가 알던 버전을 함께 보내고, 서버 버전과 다르면 409를 반환합니다.

웹앱이라 탭 두 개만 열어도 생기는 상황이고, 이게 없으면 한쪽 저장이 다른 쪽 수정을 조용히 덮어씁니다.

자동저장은 3초 디바운스인데 자기 자신과는 충돌하지 않습니다 — 응답으로 새 버전을 받아 갱신하니까요. 그리고 매번 전체를 보내지 않고 **변경된 블록만 PATCH**합니다.

### Q. 같은 파일을 두 곳에서 동시에 올리면?

`UNIQUE (owner_id, content_hash)` 충돌이 나는데, 이걸 **에러가 아니라 정상 경로**로 처리합니다. 예외를 잡아 기존 자산을 재사용하면 그게 곧 중복 제거의 정상 동작입니다.

### Q. 블록 자동 생성이 중복 실행되면?

여러 워커가 각자 마지막 자산을 끝내며 동시에 "세션 완료"를 판정할 수 있습니다. 세션 행에 `FOR UPDATE` 락을 잡고 `blocks_created_at`을 확인해서, 이미 있으면 반환합니다. **블록이 두 벌 생기는 걸 막는 유일한 방어선입니다.**

## 8. AI

### Q. AI를 어디에 썼나요?

**기록을 시작하기 쉽게 만드는 데만 썼습니다. 문장은 대신 쓰지 않습니다.**

사진을 넣으면 그날의 흐름(시각·장소·눈에 띄는 것)과 기억을 끌어내는 질문을 제시합니다. 완성된 문단은 만들지 않습니다.

이건 기술적 한계가 아니라 **제품 판단**이었습니다. 사용자가 이 기록 행위를 좋아하는 이유가 "사진을 보며 떠올리는 시간"인데, 완성된 글을 먼저 던져주면 그 시간이 사라지고 남의 글을 다듬는 작업이 됩니다. 그러면 본인부터 안 쓰게 됩니다.

### Q. AI가 실패하면요?

**핵심 경로에 두지 않았습니다.** `suggestion` 패키지 밖에서는 LLM이라는 단어가 등장하지 않고, 이 테이블이 통째로 비어 있어도 서비스는 정상 동작합니다. 사용자가 "제안 받기"를 눌렀을 때만 비동기로 호출하고, 실패하면 빈 블록으로 진행합니다.

확률적으로 실패하고 지연이 초 단위인 외부 의존성을 핵심 경로에 두면 안 된다고 봤습니다.

### Q. AI 출력 품질은 어떻게 관리했나요?

**골든셋으로 회귀 테스트를 돌렸습니다.** 검증 항목은 스키마 준수, 사진에 없는 장소명을 지어내지 않는지, 시간축이 사진 순서와 어긋나지 않는지입니다.

`suggestions` 테이블에 `prompt_ver`와 토큰·지연을 남겨서, 품질이 바뀌었을 때 어떤 프롬프트 버전이 원인인지 추적할 수 있게 했습니다.

### Q. 동시성과 정합성을 어떻게 검증했나요?

불변식을 코드로 박고 속성 기반 테스트로 돌렸습니다.

| # | 불변식 |
|---|---|
| I1 | 원본 바이트는 어떤 처리 후에도 불변 |
| I2 | 같은 내용의 파일은 물리적으로 하나만 존재 |
| I3 | 같은 원본 + 같은 레시피 버전 → 항상 같은 파생물 바이트 |
| I4 | 업로드 중단 후 재개 결과 = 무중단 결과 |
| I5 | 블록 순서키는 유일하며 정렬이 보존된다 |
| I6 | `record_days`는 블록에서 재생성해도 동일 |
| I7 | 참조가 1 이상인 자산은 절대 물리 삭제되지 않는다 |
| I8 | AI 제안은 스키마를 지키며 없는 장소명을 만들지 않는다 |

### Q. 속성 기반 테스트는 어디에 썼나요?

**쓰려고 했더니 쓸 수 없는 자리가 있었습니다.** 중복 제거 불변식(`I2`)은 "임의의 파일 묶음을 중복 섞어 임의 순서로 올려도 물리 객체는 내용 종류만큼만 생긴다"라서 속성 테스트가 딱 맞는 형태입니다. 그런데 jqwik의 `@Property`는 자체 실행 생명주기를 써서 **Spring의 JUnit 확장이 붙지 않습니다.** 컨테이너와 빈 주입이 필요한 테스트에서는 둘을 같이 쓸 수 없었습니다.

**시드를 상수로 박은 무작위 테스트로 바꿨습니다.** 잃은 것은 자동 축소(shrinking)이고, 지킨 것은 재현성입니다 — 에이전트 루프에 필요한 건 후자였습니다. 실패한 케이스를 그대로 다시 돌릴 수 있으면 되니까요.

그래서 진짜 속성 테스트는 **Spring이 필요 없는 순수 도메인** 쪽에 씁니다. 블록 순서키(`I5`)가 그런 자리인데, 컨테이너도 빈도 필요 없는 문자열 계산이라 jqwik의 축소 기능이 온전히 쓰입니다.

### Q. 테스트 환경은?

Testcontainers로 PostgreSQL과 MinIO를 띄우고, `Clock`을 주입해 시간까지 제어했습니다. **결정론적 재현이 안 되면 에이전트 루프가 아예 성립하지 않습니다** — 플래키 테스트 하나가 에이전트를 코드가 아니라 노이즈를 쫓아다니게 만듭니다.

카오스는 직접 주입했습니다. 처리 중 워커 `SIGKILL`, 스토리지 쓰기 실패, 업로드 중 연결 단절.

### Q. 골든 데이터셋은 어떻게 구성했나요?

실제 아카이브에서 나온 지저분한 파일들로 만들었습니다 — 손상된 JPEG, EXIF 없는 파일, 시간대 정보 없는 파일, 회전 플래그 붙은 이미지, HEIC, 대용량 영상, 파일명에 이모지, 같은 순간의 연사.

**합성 데이터가 아니라 진짜 쓰레기 데이터**라는 게 중요했습니다.

### Q. AI 에이전트를 개발에 어떻게 썼나요?

> **📌 실제로 돌려보고 채울 것. 아래는 준비해야 할 답변의 뼈대.**

- 에이전트에게 어떤 컨텍스트를 줘야 헤매지 않았나
- 종료 조건을 뭘로 잡았나 (테스트 통과 = 진짜 해결인가)
- 에이전트가 테스트를 무력화해서 통과시키는 걸 어떻게 막았나
- 몇 회 만에 수렴했나
- **끝내 못 고친 케이스와 그 이유** ← 가장 강력한 답변
