# 5주 로드맵 · 불변식 명세 · 에이전트 루프

> [design.md](./design.md), [pipeline.md](./pipeline.md)의 설계를 실제로 만드는 순서.

---

## 0. 범위에 대한 솔직한 평가

**MVP 전체를 5주에 넣는 것은 빠듯하다.** 웹앱이라 프론트엔드가 매주 붙는데, 이것이 예상보다 오래 걸린다.

따라서 이 로드맵은 "다 된다"를 전제하지 않는다. **§3에 잘라낼 순서를 미리 정해둔다.** 이것이 없으면 5주차에 모든 기능이 60%씩 만들어진 채 아무것도 완성되지 않은 상태가 된다.

원칙: **기능을 줄이고 깊이를 지킨다.** 얕은 기능 10개보다 검증된 기능 5개가 낫다.

---

## 1. 두 가지 원칙

### ① 매주 끝에 "돌아가는 것"이 있어야 한다

수평으로 쌓지 않는다. "1주차 DB → 2주차 서비스 → 3주차 API → 4주차 프론트"는 4주차까지 아무것도 동작하지 않고, 통합 시점에 반드시 터진다.

**매주 얇은 수직 슬라이스를 완성한다.** W1 종료 시점에 브라우저에서 실제로 사진 한 장이 올라가고 썸네일이 보여야 한다.

### ② 하네스를 W1에 시작한다

하네스를 W4에 몰아 붙이면 두 가지가 일어난다.

- 그때쯤 코드가 테스트 불가능한 모양이 되어 있다 (시간 하드코딩, 전역 상태, 스토리지 직접 호출)
- 시간이 없어 결국 대충 하게 된다

**Testcontainers와 `Clock` 주입은 W1 1일차에 넣는다.** 나중에 넣는 비용이 처음 넣는 비용의 몇 배다.

## 2. 주차별 계획

### W1 — 뼈대와 첫 수직 슬라이스

> **완료 기준: 브라우저에서 사진 1장을 올리면 썸네일이 뜬다**

| 영역 | 할 일 |
|---|---|
| 셋업 | Gradle, Spring Boot 3, Docker Compose (Postgres + MinIO) |
| **하네스** | **Testcontainers 골격, `Clock` 주입, 통합 테스트 1개** |
| 스토리지 | S3 클라이언트 추상화, 해시 기반 키, CAS 저장/조회 |
| 도메인 | `users`, `media_assets`, `media_derivatives` |
| 업로드 | 단일 파일 `PUT` (청크 없음) |
| 처리 | `PROBE`(EXIF) + `THUMB`(libvips) — **동기 실행으로 시작** |
| 인증 | 소셜 로그인 1종 |
| 프론트 | 파일 선택 + 결과 표시. 스타일 없음 |

**의도적으로 미루는 것**: 청크, 큐, 워커, 영상.
W1의 목적은 "한 장이 끝까지 흐르는 경로"를 뚫는 것이다.

**불변식 도입**: `I1`, `I2`

---

### W2 — 업로드와 파이프라인 (최대 부하 주간)

> **완료 기준: 사진 50장 + 영상 3개를 올리고, 중간에 끊어도 재개된다**

| 영역 | 할 일 |
|---|---|
| 업로드 | 청크 프로토콜, `chunk_bitmap`, 재개, 세션/항목 |
| 클라이언트 | Web Worker + `hash-wasm` 스트리밍 해싱, 해싱↔업로드 파이프라인 |
| 중복 | 해시 선조회 → `SKIPPED_DUPLICATE` → 즉시 썸네일 표시 |
| 큐 | `processing_jobs`, `SKIP LOCKED`, 워커 프로세스 분리 |
| 워커 | 레인 분리, 하트비트, lease 회수, 지수 백오프 + full jitter |
| 영상 | ffprobe, 포스터 추출, 720p 트랜스코딩, 체크포인트 |
| 알림 | LISTEN/NOTIFY → SSE, keepalive, 5초 폴링 폴백 |
| 프론트 | 업로드 진행률, 플레이스홀더 → 썸네일 교체 |

**불변식 도입**: `I3`, `I4`, `I9`

> ⚠️ **이 주가 넘칠 확률이 가장 높다.** 넘치면 영상 트랜스코딩을 W4로 미룬다. 포스터 이미지만 추출하고 재생은 원본으로 하면 일단 동작한다.

## 3. 잘라야 할 때 — 이 순서로

| 순위 | 자를 것 | 대체 |
|---|---|---|
| 1 | AI 제안 | 없어도 됨. 애초에 잎사귀 |
| 2 | 영상 트랜스코딩 | 포스터만 추출, 재생은 원본 |
| 3 | 유예 삭제 | 즉시 삭제 (참조 확인은 유지) |
| 4 | 타임라인/날짜 점프 | 기록 목록만 |
| 5 | 갤러리 레이아웃 3종 | 슬라이드 하나만 |

### 절대 자르지 않을 것

- **재개 가능 업로드** — 없으면 본인이 사용하지 않게 된다
- **워커 큐와 레인 분리** — 프로젝트의 기술적 중심
- **하네스와 불변식** — 자르면 프로젝트의 의미가 사라진다
- **W5 에이전트 루프** — 차별화의 전부

## 4. 불변식 명세

| # | 불변식 | 형태 | 도입 |
|---|---|---|---|
| I1 | 원본 바이트는 어떤 처리 후에도 불변 | 통합 | W1 |
| I2 | 같은 내용의 파일은 물리적으로 하나만 존재 | 속성 | W1 |

| I6 | `record_days`는 블록에서 재생성해도 동일 | 통합 | W3 |
| I7 | 참조가 1 이상인 자산은 절대 물리 삭제되지 않는다 | 속성 | W4 |
| I8 | AI 제안은 스키마를 지키며 없는 장소명을 만들지 않는다 | 골든셋 | W5 |
| I9 | 어떤 stage도 두 번 실행되면 최종 상태가 같다 | 속성 | W2 |
| I10 | 세션 완료 판정이 동시에 나도 블록은 한 벌만 생성된다 | 동시성 | W3 |

### I2 — 중복 저장 없음

```java
@Property
void 중복은_물리적으로_하나만_저장된다(
        @ForAll List<@From("sampleFiles") File> files,
        @ForAll("shuffledWithDuplicates") List<Integer> order) {

    order.forEach(i -> uploadAndWait(files.get(i)));

    long distinctHashes = files.stream().map(this::sha256).distinct().count();
    long storedObjects  = storage.countObjects("originals/");

    assertThat(storedObjects).isEqualTo(distinctHashes);
}
```

### I4 — 재개 동등성

```java
@Test
void 임의_지점에서_끊어도_최종_바이트가_같다() {
    var file = golden("large_video.mov");
    var expected = sha256(file);

    var session = startUpload(file);
    killConnectionAt(randomProgress());
    resumeUpload(session);

    var asset = awaitVerified(session);
    assertThat(storage.sha256(asset.storageKey())).isEqualTo(expected);
}
```

### I5 — 순서키 속성

```java
@Property
void 임의의_편집_시퀀스_후에도_순서가_보존된다(
        @ForAll("blockOperations") List<BlockOp> ops) {

    var record = newRecord();
    var expected = new ArrayList<UUID>();

    for (var op : ops) {
        applyTo(record, op);
        applyTo(expected, op);
    }

    var actual = blocks.findByRecordOrderByPosition(record.id());

    assertThat(actual).extracting(Block::id).isEqualTo(expected);   // 정렬 일치
    assertThat(positionsOf(actual)).doesNotHaveDuplicates();        // 유일성
    assertThat(maxKeyLength(actual)).isLessThan(64);                // 키 무한 성장 방지
}
```

> 마지막 단정이 중요하다. fractional index는 **같은 자리에 반복 삽입하면 키가 계속 길어진다** (`"a0"` → `"a0V"` → `"a0G"` → …). 이것을 감지하지 못하면 키가 수백 자가 된 뒤에야 재분배(rebalance) 로직이 필요함을 알게 된다.

### I9 — stage 멱등성

```java
@Property
void 어떤_stage도_두_번_실행되면_결과가_같다(@ForAll Stage stage, @ForAll("assets") Asset a) {
    runStage(stage, a);
    var after1 = snapshot(a);

    runStage(stage, a);
    var after2 = snapshot(a);

    assertThat(after2).isEqualTo(after1);
}
```

### 골든 데이터셋

실제 아카이브에서 나온 지저분한 파일로 구성한다. 합성 데이터가 아니라는 점이 중요하다.

> ⚠️ **실제 사진·영상 파일은 절대 커밋하지 않는다.** 이 저장소는 포트폴리오로 공개되고, 골든셋에는 본인과 지인의 얼굴이 담긴 사진이 들어간다. 히스토리에 한 번 들어가면 제거가 번거롭다.
>
> ```
> golden/media/          ← 실제 파일. .gitignore 대상
> golden/manifest.json   ← 해시 + 기대값. 커밋한다
> golden/expected/       ← 검증 기대치. 커밋한다
> ```
>
> ```json
> {
>   "no_exif_screenshot.png": {
>     "sha256": "3f2a...",
>     "expect": { "capturedAtSrc": "FILE_MTIME", "orientation": null }
>   },
>   "rotated_portrait.jpg": {
>     "sha256": "9c11...",
>     "expect": { "orientation": 6, "width": 3024, "height": 4032 }
>   }
> }
> ```
>
> 파일이 없는 환경(CI)에서는 골든셋 테스트를 스킵한다. 대신 **완전히 익명인 합성 샘플 몇 개**(단색 이미지에 EXIF만 조작한 것, 손상된 JPEG, 시간대 없는 파일 등)는 커밋해서 CI에서도 최소 검증이 돌게 한다.

- 손상된 JPEG
- EXIF 없는 파일 (스크린샷, 메신저 수신 이미지)
- 시간대 정보 없는 파일
- 회전 플래그가 붙은 이미지
- HEIC
- 대용량 영상 (수백 MB 이상)
- 파일명에 이모지
- 같은 순간의 연사 20장

### 결정론 체크리스트

에이전트 루프가 성립하려면 **실행할 때마다 결과가 같아야 한다.** 플래키 테스트 하나가 루프 전체를 망친다 — 에이전트가 코드가 아니라 노이즈를 쫓아다니게 된다.

- [ ] `Clock`을 빈으로 주입, 테스트에서 `Clock.fixed()`. **`Instant.now()` 직접 호출 금지**
- [ ] 백오프 지터의 랜덤 시드를 주입 가능하게
- [ ] UUID 생성기 주입 가능하게 (테스트에서 순차 생성)
- [ ] 파일 시스템 순회 순서에 의존하지 않기 (`listFiles()`는 순서 보장 없음)
- [ ] 테스트 간 DB/스토리지 격리 (컨테이너 재사용 시 truncate)
- [ ] `Thread.sleep()` 대신 Awaitility

> 마지막 항목이 플래키의 최대 원인이다. `sleep(500)`은 느린 CI에서 반드시 터진다.

### 가드 ① — 검증 코드 수정 금지

에이전트에게 "테스트를 통과시켜라"라고 하면 가장 쉬운 길은 **테스트를 고치는 것**이다. 단정을 느슨하게 하거나, `@Disabled`를 붙이거나, 기대값을 실제값으로 바꾼다. 초록불은 뜨지만 아무것도 고쳐지지 않는다.

```bash
if ! git diff --quiet -- src/test/ golden/; then
  echo "ABORT: 에이전트가 검증 코드를 수정했습니다"
  git checkout -- src/test/ golden/
  exit 1
fi
```

### 가드 ② — 성능 회귀 감지

더 미묘하다. 동시성 테스트를 통과시키는 가장 쉬운 방법은 **락 범위를 넓히는 것**이다. 정합성은 맞는데 처리량이 절반이 된다.

```java
@Test
void 처리량이_기준선_대비_20퍼센트_이상_떨어지지_않는다() {
    var elapsed = measure(() -> processAssets(goldenSet.photos(50)));
    assertThat(elapsed).isLessThan(baseline.multipliedBy(120).dividedBy(100));
}
```

> **이 두 가드를 만든 경험 자체가 면접 답변이다.** "에이전트가 테스트를 무력화하는 것을 어떻게 막았나요?"는 실제로 해본 사람만 답할 수 있다.

### 기록할 것 — W5의 진짜 산출물

- 각 실패에 대해 몇 회 만에 수렴했나
- **수렴하지 못한 케이스와 그 이유**
- 에이전트가 시도했다가 가드에 걸린 우회 방법들
- 컨텍스트를 얼마나 줬을 때 가장 잘 동작했나
- 플래키 테스트가 루프에 미친 영향

> **"에이전트가 끝내 못 고친 케이스"를 설명할 수 있는 사람이 진짜 써본 사람이다.**

## 7. 측정할 숫자

README에 들어갈 것. **숫자 없는 포트폴리오는 절반짜리다.**

| 항목 | 기록할 것 |
|---|---|
| 처리 | 사진 70장 업로드 → 전부 `READY`까지 걸린 시간 |
| 체감 | 첫 썸네일이 화면에 뜨기까지 걸린 시간 |
| **레인 효과** | **레인 분리 전/후 "사진이 다 뜨는 시간" 비교** |
| 중복 제거 | 재개 시나리오에서 절약된 전송 바이트 |
| 영상 | 45초 4K 영상 트랜스코딩 소요 시간 |
| 스토리지 | 원본 대비 파생물 용량 비율 |
| 에이전트 | 평균 수렴 횟수, 성공률, 실패 유형 분포 |

> **"레인 분리 전/후"는 반드시 측정할 것.** "왜 나눴나요?"에 대한 가장 강력한 답이 된다. 설명이 아니라 숫자이기 때문이다.
